# Préparation d’exploitation — aucune publication effectuée

La recette utilise Supabase local sur API55321, PostgreSQL55322, Studio55323, Mailpit55324, projet Docker n91-matchlab-local. `npm run matchlab:setup` crée seulement un compte fictif aléatoire ; les migrations locales ne doivent jamais être dirigées vers le projet du club.

MatchLab réutilise par défaut le projet Supabase déjà configuré pour le site : `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` et `SUPABASE_SERVICE_ROLE_KEY`. Il n’est pas nécessaire de dupliquer ces valeurs sur Vercel. La clé de service reste exclusivement côté serveur. Ce partage de projet conserve les cookies, habilitations et politiques RLS propres à MatchLab ; un compte de la vitrine ne devient pas automatiquement membre du staff.

Pour un environnement distinct (notamment la recette locale), renseigner ensemble `MATCHLAB_SUPABASE_URL`, `MATCHLAB_SUPABASE_ANON_KEY` et `MATCHLAB_SUPABASE_SERVICE_ROLE_KEY`. Dès qu’une de ces valeurs est présente, cette famille devient prioritaire : une configuration partielle est refusée par les opérations qui ont besoin des valeurs manquantes, sans mélange entre projets. La sélection est commune aux sessions, au proxy, au CMS et au bootstrap. Les tests locaux continuent à imposer `127.0.0.1:55321`.

Avant l’activation dans un environnement hébergé autorisé : sauvegarder son état, examiner/appliquer les migrations additives dans l’ordre et configurer `MATCHLAB_APP_ORIGIN` à l’origine HTTPS exacte (par exemple `https://ninetyfour.vercel.app` si c’est le domaine utilisé). Configurer l’URL de callback `/api/matchlab/auth/callback` dans Supabase Auth et SMTP. La présence des variables ne crée ni les tables MatchLab ni les habilitations ; ces étapes restent explicites. La branche de développement est codex/matchlab. La migration `202610170012_match_updated_at.sql` crée la fonction `ml_touch_updated_at`, utilisée par les migrations 0014, 0015, 0017 et 0018 : l’appliquer en premier si elle manque (sinon : « function public.ml_touch_updated_at() does not exist »). La migration `202610180013_photo_access.sql` (droit médias de la direction, photos sans prérequis de gouvernance, consentement toujours exigé) doit être appliquée avant d’utiliser l’ajout de photo simplifié ; sans elle, l’interface affiche l’erreur de gouvernance ou d’habilitation renvoyée par la base. Appliquer ensuite `202610180014_squad.sql` (terrain tactique, référentiel d’essai, décisions d’essai) puis `202610180015_video.sql` (bucket vidéo privé, séquences) `202610180016_dossier.sql` (dossiers club, autorisation de diffusion) `202610180017_live.sql` (match en direct) `202610180018_plans.sql` (cellule tactique) et `202610180019_assistant.sql` (journal de l’assistant). L’aperçu caméra du direct exige HTTPS (contexte sécurisé du navigateur). Pour la vidéo, relever la limite d’envoi du projet Supabase (Storage, « Upload file size limit ») au-delà de la taille des vidéos de match et vérifier que le plan couvre le volume stocké ; la durée de conservation et la politique de consentement doivent être définies dans Administration avant le premier import.

Build Vercel prévu : `next build --webpack`, Node24 conseillé (recette24.14.1), lockfile versionné, `npm ci`. Le build normal lit .env.local en local ; le lanceur MatchLab fournit ses variables dédiées sans modifier les secrets existants. Éviter deux processus Next écrivant dans le même .next.

## Premier administrateur

Créer ou choisir explicitement une identité Supabase existante dans l’environnement visé. Aucun mot de passe commun, aucune promotion automatique. Exécuter volontairement `node --env-file=<fichier-dédié> scripts/matchlab-bootstrap.mjs <UUID-utilisateur>`. Le script refuse lorsqu’une direction active existe déjà ; les habilitations suivantes passent par l’écran audité. Les rôles de la vitrine ne sont pas modifiés.

Configurer la gouvernance avant des médias réels. Importer et vérifier les six articles puis activer MATCHLAB_CMS_ENABLED. Conserver MATCHLAB_PUSH_ENABLED=false tant que l’adaptateur d’envoi Push n’est pas développé et validé ; le worker ne cache aucun contenu privé. Aucun endpoint IA à configurer : moteur volontairement absent.

Prévoir sauvegarde PostgreSQL + bucket privé, stockage chiffré des archives, durée/effacement approuvés et revue des dépendances résiduelles. Les migrations distantes et le déploiement constituent une phase séparée, non exécutée ici.
